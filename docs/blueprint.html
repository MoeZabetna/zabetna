Product & technical blueprint

Zabetna

A discount platform connecting users to participating shops, restaurants, and service categories through in-app offers redeemed in person. Three surfaces share one backend: a consumer app, a merchant verification app, and an operations admin panel.

Stack decided Schema live on Supabase Admin Panel core live — Categories + Shops 19 demo shops seeded (Beirut) zabetna.com not connected anywhere 20 of 21 User App screens remaining

Read this straight: what follows is the framework — a shared reference so every decision from here (schema, screens, permissions) is built once, correctly, instead of guessed at per-feature. It is not a finished app. The roadmap in §06 is the honest sequence for getting from here to a working v1.

01 — Product scope

Three surfaces, one source of truth

Each surface has a distinct job and a distinct user. All three read and write the same backend — nothing is duplicated or synced by hand.

User App

Consumer-facing. Browse categories, discover shops, view and save offers, redeem via QR at checkout.

  • Category & shop browsing, search, geolocation
  • Offer detail, favorites, redemption history
  • QR generation at point of redemption
  • Profile, notifications

Restaurant / Shop App

Merchant-facing. Used by shop staff to verify and log redemptions in real time.

  • Staff login, scoped to one shop
  • QR scanner, redemption verification
  • Live usage log for that shop
  • Own-shop offer status (read-only or limited edit)

Admin Panel core live

Operations-facing, web-based (Next.js). Runs the platform: onboarding, content, and oversight.

  • Live: RBAC-aware login; category management (add/edit/delete, drag-free up/down reorder, icon picker from a 30-icon set)
  • Live: shop onboarding — name, category, description, address, phone, status, and an interactive map pin (Leaflet/OpenStreetMap, no API key) for the exact geolocation
  • Not yet built: banners, featured listings (top 3/category), overall + per-shop reporting, admin user invite/permission management — all stubbed as "Coming Soon" behind the same RBAC gates
02 — System architecture

One backend, three clients

The mobile apps and admin panel are thin clients over a single Supabase project. This keeps the data model, auth, and business rules (redemption validity, usage limits) in one place instead of re-implemented per app.

Shared TypeScript types are generated straight from the Postgres schema (supabase gen types) and consumed by all three apps via a shared package, so a schema change surfaces as a type error in every client immediately rather than as a runtime bug in one of them.

Every table above ships with Row-Level Security policies — a user can only read/write their own profile, favorites, and redemptions; shop staff can only touch their own shop's offers and redemptions; admin access is gated by role_permissions, checked at the database layer, not just hidden in the UI. This matters because it means a bug in the admin panel's UI can't accidentally expose another shop's data — the database refuses the query regardless.

04 — Redemption flow

QR-based, time-boxed, single-use

This is the one flow where a design mistake becomes real money lost, so it gets the most explicit spec. A generated code is worthless as fraud protection unless it expires, is bound to one shop, and can only ever be marked verified once.

1

User taps "Redeem" on an offer User App

Client calls a create_redemption edge function — never writes the redemption row directly. The function checks the offer is active, within its date window, and under both the per-user and total usage limits before doing anything else.

2

Server issues a short-lived token Edge Function

A redemptions row is created with status pending, a random single-use token, and expires_at ~3 minutes out. The token — not the offer ID — is what gets encoded in the QR code.

3

QR renders on the User App

The app shows a live countdown alongside the code, so the user understands it must be scanned promptly — this is a fraud control, not a UX afterthought.

4

Staff scans the code Restaurant App

The scan calls verify_redemption with the token and the scanning staff member's shop_id. The function rejects the scan outright if the token's shop doesn't match — a code generated for Shop A cannot be redeemed at Shop B, even by an authenticated staff account elsewhere.

5

Server verifies and locks the row

Checks: not expired, status still pending, limits not exceeded since issuance. On success, status flips to verified atomically (row-level lock, so two near-simultaneous scans can't both succeed) and verified_by / verified_at are recorded.

6

Both apps update in real time

A Supabase Realtime subscription pushes the status change straight to the User App, which flips from countdown to a confirmation screen with no polling and no manual refresh.

Explicitly out of scope for v1, flagged for later: GPS-proximity checks (confirming the user's device is actually near the shop at scan time) and device-fingerprint rate limiting. Both are real anti-fraud upgrades worth adding once usage volume justifies the engineering cost — building them into v1 would slow the first launch for a risk that's low at low volume.

05 — Admin roles & permissions

Role-based access, enforced twice

Permissions are checked in the Admin Panel UI (so people don't see controls they can't use) and in Postgres RLS (so a UI bug is never a security hole). Roles below are starting defaults — admin_roles is a table, not an enum, so operations can define new roles without an engineering change.

06 — Build roadmap

Six phases, in dependency order

Ordered by what actually blocks what — reporting can't be built before redemptions exist, redemptions can't be verified before the Restaurant App has staff auth, and none of it means anything without a schema underneath it. Each phase has an explicit "done when," not a vague sense of progress.

Foundation

Repo scaffold, Supabase project provisioned, schema applied as migrations with RLS, design tokens pulled from Figma, CI skeleton.

Done when: a developer can clone the repo, run one setup command, and hit a live (empty) database from all three app shells.

Admin auth, role/permission system, category CRUD, shop onboarding & approval queue, admin user management.

Done when: ops can onboard a real shop end-to-end without a developer touching the database. Shop onboarding itself: done. Approval workflow, banners, reporting, and admin management remain.
02

Auth (OTP), category/shop browse, search, shop detail, offer detail, favorites, profile — matched to the Figma design.

Done when: a user can sign up, find a shop, and read a real offer's terms end-to-end.
03

Redemption loop

QR generation, Restaurant App staff auth + scanner, the full verify flow in §04, realtime status sync.

Done when: a real redemption can happen end-to-end between two physical devices.
04

Reporting

Per-shop dashboard (their own redemptions only, via RLS), overall admin reporting, CSV export.

Done when: a shop owner and Super Admin can both answer "how many redemptions this week" without asking a developer.
05

Merchandising & polish

Banners, featured listings (top 3 per category), push notifications, empty/error states, accessibility pass.

06

Load/security testing on the redemption path specifically, rate limiting, app store submission assets and review.

Done when: both apps pass store review and the redemption endpoint survives a deliberate abuse test.
